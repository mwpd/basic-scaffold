It started with one feature: warn readers that an old post may be out of date. Then editors wanted a column in the Posts list, a setting, and a weekly email.

aTwo lifecycle facts make code like this hard to get right. Many conditions only answer after a certain point: is_singular() means nothing until the query has run. And WP-Cron runs in its own request to wp-cron.php, where is_admin() is false, so the digest callback above is never there when the event fires.

Every line that decides when or whether lives next to every other such line. The column has to stay out of the notice's way, the digest has to survive the column's is_admin(), and none of it can be tested without the rest. The fourth feature has to know about three. The tenth has to know about nine.

First feature

The notice decides for itself where it belongs.

The notice is needed on a single post, and WordPress can only say whether this is a single post once the query has run. So the service says both, as static answers the plugin can ask before it builds anything.

It never checks is_admin(). It does not fetch the post when it is built: MainLoop tells it, while the_content runs, whether this is the queried post in the main loop, so a related-posts block further down gets no notice.

Second feature

The column is one more service and one more line.

The Posts list column lives in a different part of WordPress, on an admin screen that is only known once current_screen fires. It says so, the same way. The composition root gains one entry; the notice is not touched.

Third feature

The digest needs the plugin's lifecycle, not a request.

A weekly email is scheduled when the plugin is activated and cleared when it is deactivated, in each site: every site has its own posts, editors and cron events. The service says that by implementing SiteActivateable and SiteDeactivateable, and the scaffold calls it in every site an activation or deactivation reaches, a whole network included.

It is deliberately not Conditional. WP-Cron fires the event in whatever request comes along, so the callback has to be hooked in every request, and the lifecycle events skip a Conditional service that is not needed in the site they reach.

bThe fourth service, FreshnessSetting, is Delayed to admin_init and not Conditional: waiting for admin_init already keeps it out of the front end, and an is_admin() condition would stop it from cleaning up when the plugin is deleted through WP-CLI.

The fourth feature, the setting under Settings › Reading, went in the same way. Removing its option when the plugin is deleted is a lifecycle point too, and the scaffold covers it with a capability interface, never a condition inside a service: the setting implements SiteUninstallable, and the scaffold's static uninstall bridge reaches it in every site when the plugin is deleted.

That staircase is the whole point. Each feature was one more service that manages its own lifecycle. Complexity grew by one service at a time, not by one more condition in every existing one.

The lifecycle questions a service can answer

Is it needed in this request at all?
Conditional::is_needed(). Asked before the service is built. If the answer is no, the service never exists.
When does it hook in?
Delayed::get_registration_action(), at get_registration_priority(). Registration waits for that action, or runs at once if it has already fired.
Which services must exist first?
HasDependencies::get_dependencies(). Registration waits until they are registered, and fails loudly when they never can be.
What does it hook into?
Registerable::register(). Called once the service is built, to add its actions and filters.
What happens on activation?
Activateable::activate(), once, or SiteActivateable::activate_site() in every site the activation reaches. Safe to run twice.
And on deactivation?
Deactivateable::deactivate(), or SiteDeactivateable::deactivate_site() in every site, the same way.
And when the plugin is deleted?
SiteUninstallable::uninstall_site() in every site, through a static uninstall bridge. Safe to run twice.

The questions are static methods on purpose, so the plugin can decide before it builds. A service a request does not need is never instantiated, which is what Figure 1 shows: each request pays only for the services it uses.

One composition root.

The plugin class implements no features. It lists the services and tells a small injector how to assemble them, in one place.

cThe injector and the service container are small in-house implementations behind interfaces. ServiceBasedPlugin takes any Injector and ServiceContainer through its constructor and falls back to the simple ones when none is passed.

Services ask for interfaces in their constructors. The notice, the column and the digest all ask for a FreshnessPolicy; the highlighted line decides which one they get. new is reserved for value objects and exceptions, the inside of factories, and the built-in default a constructor falls back to. Everything else comes from the injector, so there is one place to read when you want to know how the plugin fits together.

Architecture that is checked, not just documented.

38 architecture rules, as PHPStan rules and an architecture test suite, run in composer lint, composer test and CI. A failure never only says no.

Here is the column as a coding agent might first write it, the way most plugins do: no lifecycle declarations, and an is_admin() guard at the top of register().

dSome of the other mistakes the rules catch: a hook added in a constructor, new of a service inside another service, a class that is not final, a bare SPL exception, a public WordPress name without the plugin's prefix, HTML printed by a service, a subsystem service missing from the composition root, a delayed service waiting for a misspelled action.

Every failure has the same three parts: what is wrong and where, what to do instead, and why, with links to the principle, to the pattern that meets the need the rejected code was after, and to the rule's own entry.

The rules cannot be silenced inline or baselined. architecture.noSuppression rejects an @phpstan-ignore or an ignoreErrors entry aimed at an architecture rule, and architecture.gatesAtStrength fails the build if PHPStan drops below max, Psalm rises above level 2, or a baseline appears. A real exception becomes reviewed configuration under parameters.architecture in phpstan.neon.dist, where it stays visible.

Around the architecture rules: PHPStan at max, Psalm at level 2, the WordPress Coding Standards and PHPCompatibility for 7.4, and PHPUnit on PHP 7.4 and 8.3, all in CI.

Answers indexed by need

docs/patterns.md has 20 sections named the way the problem is phrased: “I need a singleton”, “I need a service locator”, “I need to hook in later”. Each gives the scaffold's answer, with code that passes the checks.

A feedback loop that teaches

When an agent reaches for the wrong pattern, the check fails with the fix and a link to the pattern. The agent corrects itself in the next iteration instead of shipping it.

Agents assemble plugins the right way for the same reason people do: the architecture is written down where they look first, the fix is in the error, and the gate does not open until it is applied.

The WordPress anti-patterns, and what to do instead.

From principle 7 of the design principles. In a review, an item from the left column is a defect even if the code works.

Common in pluginsIn the scaffold
Hooks registered in a constructor
Constructors only store dependencies. Hooks go in register(), called by the plugin at the right time.
A singleton with ::instance() and static state
Shared instances come from the injector. The plugin factory keeps one plugin instance without the Singleton pattern.
A service locator, such as Services::get( 'id' )
Each need behind it has its own answer: constructor injection, a factory, a typed registry, a shared instance, or a bridge at the edge of the graph.
A global or singleton so WordPress callbacks can reach the plugin
A bridge in the main file gets the plugin through the plugin factory and delegates at once, as the activation hooks do.
new for collaborators inside a class, or pulling them from globals
Dependencies arrive through the constructor and are configured as bindings in the composition root.
is_admin() wrapped around hook calls throughout the code
The service states when it is needed once, in Conditional::is_needed().
Hooking an early action just to wait for a later one
The service names its registration action through Delayed, and the plugin defers it.
Query-dependent checks before the query has run
A Conditional service also implements Delayed and returns wp or later, so the plugin waits before asking.
Work done when a file is included
Only the main plugin file has side effects. Everything else is autoloadable declarations.
One god class holding the whole plugin
A composition root wires small services, each with one responsibility.
Echoing HTML from business logic
Output goes through views from a ViewFactory, escaped by default.

Runs on PHP and WordPress alone.

Copy the plugin directory and activate it. There is no build step on the server and nothing to install there.

Requirements
PHP 7.4 or later, WordPress 6.0 or later. The code is written to the 7.4 floor and PHPCompatibility checks it.
Runtime dependencies
None. composer.json requires nothing but PHP. Composer is a development tool for tests, static analysis and coding standards.
Autoloading
The Composer autoloader when vendor/ is present; the bundled Infrastructure\Autoloader when it is not. CI proves the second path on PHP 7.4 without installing anything.
Views
Escaped by default; raw() is the explicit exception. Templates can be overridden from the child theme, then the parent theme, then the plugin.
Errors
Typed exceptions on PHP's SPL hierarchy, one marker interface, named constructors. Loud with WP_DEBUG on; with it off, the broken part degrades and the page around it stays up.
Infrastructure
Injector, container, views and autoloader are small in-house implementations behind interfaces, so a stronger one can replace any of them when a real need appears.

Your next plugin, from this one.

eThe checks are configured by namespace. Once step 1 renames it in phpstan.neon.dist, every rule on this page applies to your code, and to whatever your agent writes next.
  1. Make it yours. Rename the plugin header and file name in basic-scaffold.php, the MWPD\BasicScaffold namespace in src/, tests/ and composer.json, the namespaces under parameters.architecture in phpstan.neon.dist, the BasicScaffoldPlugin, BasicScaffoldPluginFactory and BasicScaffoldException classes, and the HOOK_PREFIX and SERVICE_PREFIX constants.
  2. Replace the samples. Swap the services in src/SampleSubsystem/ and the templates in views/ for your own. Content Freshness's history shows the whole journey, one commit per step.
  3. List your services in BasicScaffoldPlugin::get_service_classes(). Then keep adding one per feature.

Add the next feature. Change nothing else.
